rossedman/strata

Every image's lineage
and staleness.

strata indexes a container registry into one local file and tells platform teams what each image is built on and whether it has gone stale. From registry metadata alone, with the reasons spelled out. Browse it in the web UI, script it from the CLI, or hand it to an agent over MCP.

The problem

A million images.
No idea what they're built on.

Registries only know where a tag points now. Which images still run on last month's base, which bases quietly forked, and which builds nobody pulls any more are invisible, until a CVE lands in a base and someone has to find everything built on it. strata reads the layer stacks the registry already stores and turns them into a graph you can query.

Core ideas

Three questions,
one index.

One crawl fetches every manifest and config once, by digest. Lineage, staleness and every query are views over that index, recomputed when something changes.

Where did it come from?

Lineage from layers

An image's parent is the indexed image whose whole layer stack is the longest exact prefix of its own, matched by chain ID. Annotations and labels add declared parents, and disagreements are flagged.

strata ancestry payments/api:1.8.2
strata descendants base/go:1.22 \
  --all-versions --depth 0

Is it stale?

Explainable verdicts

Base drift, supersession, untagged leaves, EOL roots and label policy combine into fresh, drifting, stale or abandoned through a policy file you tune per repo or label.

strata stale --group-by label.team
strata query 'stale.base_drift'

What is it?

Labels are query fields

Every config label and annotation is a field, next to config, referrers, ancestry and staleness. Filters compile to SQL and run inside DuckDB.

strata query 'label.team = "payments"
  and age > 180d and not has:sbom'

Why strata

Read-only by design.
Fast where it counts.
